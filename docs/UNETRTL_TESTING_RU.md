# Ручная приёмка UNETRTL.DLL в MAME / на железе

Документ — developer-only: он не входит в `DIST_DOC_FILES` и не попадает
в ZIP/floppy image. Дополняет `docs/UNETRTL.md` (описание ABI) и
`docs/MAME_NETWORK.md` (общая настройка сети MAME); здесь -- только
сценарии для проверки `UNETRTL.DLL` через её штатный клиент
`UNETTEST.EXE` (`src/apps/unettest.asm`).

Автоматический гейт перед любой сессией:

```sh
make clean
make test-host package image
```

`make test-host` уже проверяет `UNETRTL.DLL`/`UNETTEST.EXE` под host-side
Z80-эмулятором (`tools/test-exe-dll.js`, `docs/HARNESS.md`) -- это быстрый,
но не заменяющий MAME сигнал. Ниже -- сценарии для реального MAME
(`-isa1 rtl8019as`) или платы, когда она появится.

## Что уже покрыто автоматически (история багов)

`tools/test-exe-dll.js` прогоняет через JS-harness ПОЛНЫЙ путь DLL:
NETINIT (включая загрузку cold-оверлея из хвоста файла DLL), GETCAPS,
RESOLVE (литеральный IP), PING, CONNECT/SEND/RECV/CLOSE, UDP-эхо
(21 и 1472 байта), `-l` (LISTEN/UNLISTEN, таймауты accept-ожидания) и
`-a` (SETOPT SENDSLICE + CONNECT + SEND). Три бага, которые эти векторы
однажды поймали и теперь держат как регрессионные:

- **`CHECK_ASYNC_PEND` затирал `A` перед `CHECK_CHANNEL`** -- каждый
  `CONNECT`/`CLOSE`/`UDPOPEN`/`LISTEN`/`UNLISTEN` возвращал `NERR_PARAM`
  не отправив ни байта. Исправлено (A сохраняется через L).
- **`PUT_DEC_HL` в `unettest.asm` оставляет `DE=0`** -- `-u`-поток
  грузил указатель payload до печати размера, и `SEND` уходил с 21
  байтом, прочитанным с адреса `0x0000`. Исправлено (аргументы
  грузятся после всей печати).
- **"BIOS call while ISA window is open (fn=0x0F)"** оказалась ложным
  срабатыванием самого харнесса: cold-оверлей легально исполняет свой
  диспатчер по адресам `0x0008`/`0x0010` при перемапленном окне 0, а
  харнесс трактовал любое попадание PC на RST-вектора как сервисный
  вызов. Исправлено в `tools/exe-harness/harness.js`.

Ниже -- сценарии для реального MAME/железа: то, что harness покрыть не
может (настоящий входящий accept для `-l`, настоящий `NERR_AGAIN` при
закрытом TCP-окне для `-a`, тайминги реальной сети).

## Подготовка стенда

Один раз после перезагрузки macOS (или если `feth0`/`feth1` пропали):

```sh
./tools/dev/init_interfaces.sh
```

Поднимает `feth0`/`feth1` (`192.168.7.1/24` на стороне хоста), права на
`/dev/bpf*`, NAT/forwarding на WAN (нужен, только если сценарий ниже
использует внешние ресурсы -- локальные сценарии этого документа обходятся
без него). Подробности и cleanup -- `docs/MAME_NETWORK.md`.

Привязать MAME к `feth0` (Tab -> Network Devices -> rtl8019as -> feth0),
один раз -- сохраняется в `cfg/sprinter.cfg`.

**Важно: `run_sprinter_rtl8019as.sh` сам по себе НЕ подключает
`distr/sprinter-rtl8019a.img`.** Скрипт грузит две персистентные CHD
(`sp_hdd_sys.chd` как C:, `sp_hdd_media.chd` как D:) -- это общий,
не связанный с этим репозиторием рабочий стол Sprinter DSS, куда файлы
разных проектов копировались вручную в разное время (например
`C:\RTL1`, `C:\RTL2` содержат СТАРЫЕ копии этого проекта). Второй
флоппи-привод (`beta:wd179x:1`, уже настроен как `35hd` -- 3.5" HD, тот
же формат, что и наш FAT12-образ) занят посторонним `solid.img`.
Свежий билд из `make image` нужно подключить явно:

```sh
/Users/dmitry/dev/zx/sprinter/mame/run_sprinter_rtl8019as.sh \
  -networkprovider pcap \
  -flop2 /Users/dmitry/dev/zx/sprinter/sprinter-rtl8019a/distr/sprinter-rtl8019a.img
```

(скрипт передаёt лишние аргументы напрямую в MAME, а более поздний
`-flop2` перекрывает встроенный `solid.img` -- сам скрипт трогать не
нужно). Это ставит наш собранный образ в дисковод **B:**. Работать
прямо с B: -- он уже содержит все утилиты и `NETSMPL.CFG`, ничего
докопировать не нужно (в отличие от C:\RTL1/RTL2, где лежат устаревшие
билды многонедельной давности -- их использовать не надо, они не
отражают текущий код).

В DSS: `B:`, затем `COPY NETSMPL.CFG NET.CFG`, прописать
`IP=192.168.7.2`, `NETMASK=255.255.255.0`, `GATEWAY=192.168.7.1`,
затем `NETCFG -i -v` и `IFUP` (или чистый `NETCFG -c -v` +
`NETCFG -i -v`, если `IFUP`/DHCP не нужен для этой сессии -- UNETRTL
сам DHCP не делает, ему достаточно опубликованного статического
окружения). Каждый цикл `make image` перезаписывает
`distr/sprinter-rtl8019a.img` на диске -- следующий запуск MAME с той
же `-flop2` командой сразу видит свежий билд, повторный COPY не нужен.

Во всех сценариях ниже вызывайте `UNETTEST` с **литеральным IP**
(`192.168.7.1`), а не `example.com` (значение по умолчанию): `resolve_lib`
(`src/lib/resolve_lib.asm`) сначала пробует распарсить аргумент как
`a.b.c.d`, и только при неудаче идёт в DNS -- так сценарий не зависит от
DNS-инфраструктуры и требует только ARP+ICMP, которые за `192.168.7.1`
и так отвечает сетевой стек macOS (см. "Сеть на feth-паре" в
`docs/MAME_NETWORK.md`) -- никакого дополнительного responder-а для
`RESOLVE`/`PING` не нужно.

## Сценарий 0: первым делом -- преамбула до connect

```text
UNETTEST 192.168.7.1 80
```

Смотреть строго до `connect 192.168.7.1:80`:

```text
UNETTEST - universal network DLL smoke test
Loading ...UNETRTL.DLL
DLL: UNETRTL  v...
caps=0x023F
abi=0x0100
net: ...
NETINIT ok
IP: 192.168.7.2
resolve: 192.168.7.1
ping: <N> ms
connect 192.168.7.1:80
```

Если MAME зависает/крашится раньше `NETINIT ok` -- сохранить
скриншот/лог MAME на этом самом месте, это самостоятельная находка
(harness такой сбой больше не предсказывает). Если дошло до
`connect ...` -- переходить к сценарию A ниже.

## Сценарий A: TCP (CONNECT/SEND/RECV)

Терминал 1 (responder):

```sh
sudo python3 tools/dev/unettest_tcp_probe.py --bind 192.168.7.1 --port 80
```

Дождаться `READY mode=echo bind=192.168.7.1:80`. Терминал 2 (опционально,
для независимого подтверждения по проводу):

```sh
sudo tcpdump -i feth1 -nn -vv tcp port 80
```

В DSS: `UNETTEST 192.168.7.1 80`.

**Ожидаемо:** терминал 1 показывает `CONN from 192.168.7.2:...`, затем
`REQ (... bytes, matches UNETTEST shape=True): b'HEAD / HTTP/1.0\r\nHost:
192.168.7.1\r\n...'`, затем `REPLIED and closed`; в DSS -- `request
sent`, `--- reply ---` и HTTP-заголовки ответа, затем `--- closed ---`,
`done.`. Если `Connect failed.` при полном молчании responder-а (tcpdump
не видит SYN) -- байт не ушёл в сеть вовсе: это локальная проблема
DLL/драйвера, фиксировать с полным выводом отдельно.

Контрольный запуск (baseline для сравнения) -- эмулировать реальный
обрыв соединения после успешного `CONNECT`:

```sh
sudo python3 tools/dev/unettest_tcp_probe.py --bind 192.168.7.1 --port 80 --mode abort
```

Подтверждает, что `SEND`/`RECV` на разорванном соединении в `UNETTEST`
никогда не показывают `NERR_PARAM`. Проверять нужно именно это, а не
конкретную строку: какая из двух операций поймает обрыв, решает гонка
между RST и очередным вызовом, и обе ветки одинаково правильные.

- **RST приходит после `SEND`.** `SEND` отрабатывает успешно, а первый
  же `RECV` получает `NERR_CLOSED` (`DE=0`) и коротким путём сразу
  печатает `--- closed ---` -- без отдельной строки
  `receive error`/`lasterr`, это ожидаемо (см.
  `.recv_closed_data`/`.recv_closed` в `unettest.asm`). Так обычно
  ведёт себя MAME.
- **RST приходит до `SEND`.** Тогда падает сам `SEND`: `Send failed.`
  и строка вида

  ```text
  lasterr: RTL hw=0/#0300 st=SEND nerr=07 tcp=03 res=00 tx=04/02/03/22
  ```

  Так обычно ведёт себя реальное железо: настоящая сеть отвечает
  быстрее, чем Спринтер доходит до следующего вызова. `nerr=07` -- это
  `NERR_CLOSED`, `tcp=03` -- `F_RST` (`tcp_lib.asm`), то есть DLL
  правильно назвала причиной RST пира. В `tx=` первые два байта --
  stage и raw ISR: `ISR=0x02` (`PTX`) означает, что последний кадр ушёл
  в эфир нормально и передатчик тут ни при чём.

Находкой считать только `NERR_PARAM` (09), зависание, либо `nerr=07`
без `tcp=03` -- последнее означало бы, что соединение закрылось не по
RST, а по чему-то, чего в этом сценарии быть не должно.

## Сценарий B: UDP (`-u`)

Терминал 1:

```sh
sudo python3 tools/dev/udp_echo.py --bind 192.168.7.1 --port 7777
```

В DSS: `UNETTEST -u 7777 192.168.7.1`. Ожидать `udp poll0 ok`,
`request sent`, `udp reply: len=21 data=SPRINTER UNETTEST UDP`,
`udp echo ok`. Дополнительно повторить с явным размером
(`UNETTEST -u 7777 1472 192.168.7.1`) -- проверяет zero-copy путь на
границе стандартного MTU -- и `UNETTEST -u 7777 1473 192.168.7.1`, где
ожидается локальный `NERR_PARAM` от самого бэкенда (payload больше
лимита), см. `docs/UNETRTL.md`.

## Сценарий C: два канала (`-2`, MULTICHAN)

Терминал 1:

```sh
python3 tools/dev/dual_server.py --host 192.168.7.1 --control-port 9099 --data-port 9100
```

(остальные флаги -- см. `tools/dev/dual_server.py --help`; порт по
умолчанию 9099 -- control, 9100 -- data). В DSS:
`UNETTEST -2 9100 192.168.7.1 9099`. Ожидать `dual channel ports
9099/9100`, оба `connect ...`, `request sent`, `reply rode our ACK`/`no
reply on our ACK`, поток `data bytes: N` + `data stream continuous`,
`control reply: ...`.

Строка про ACK -- диагностический зонд, а не критерий приёмки.
Сценарий C закрывается по `data bytes`, `data stream continuous` и
`control reply:`; обе формулировки про ACK допустимы.

Зонд сообщает, попал ли прогон в состояние, где ответ пира приехал
**на ACK нашей же команды**: тогда бэкенд захватывает его в pend-слот
прямо внутри `SEND`, и это ровно то состояние, в котором pend-guard
когда-то отказывался досылать уже улетевшие данные. Попробовать в него
попасть можно так:

```sh
python3 tools/dev/dual_server.py --host 192.168.7.1 --control-port 9099 --data-port 9100 --lockstep
```

`--lockstep` заставляет сервер ответить сразу, а не в середине потока.
Но управляет он только моментом ответа **приложения**, а не моментом,
когда **ядро хоста** пошлёт ACK. Если стек хоста успел подтвердить
команду раньше, чем Python дошёл до `sendall`, ответ приедет отдельным
сегментом уже после возврата из `SEND`, и `UNETTEST` напечатает `not
hit`. Это не сбой: в такое состояние прогон просто не попал (см.
комментарий у `MSG_ACK_RIDE` в `unettest.asm`).

**Проверено 2026-09-09: с macOS-хоста эта ветка не воспроизводится.**
Не тратьте на неё время заново. Испробовано и не помогло:

- `--lockstep` -- сервер отвечает немедленно, в логе видно `lockstep:
  replied immediately (31 bytes)`, на стороне DSS всё равно `not hit`;
- дополнительно `sudo sysctl -w net.inet.tcp.delayed_ack=1` (вернуть
  `=3`) -- результат тот же.

Причина в том, что из userspace нельзя управлять моментом ACK: ядро
подтверждает нашу команду раньше, чем Python успевает ответить, и
ответ приезжает отдельным сегментом уже после возврата из `SEND`. Что
`RXPEND` в принципе работает, видно ниже по тому же экрану -- строка
`control reply pending (STATUS RXPEND)` появляется штатно, просто позже.

Детерминированно попасть в это состояние можно только там, где тайминг
задаётся, а не наблюдается: в harness (`respondTcp` в
`tools/exe-harness/net-builders.js` уже держит несколько сессий по
портам, не хватает вектора для `-2` и режима «ответ уезжает на ACK»).
Пока такого вектора нет, в evidence записывать: ветка pend-guard на
железе не покрыта.

## Сценарий D: passive open (`-l`, LISTEN/UNLISTEN)

`UNETTEST -l LISTENPORT` арендует `LISTENPORT` на канале 0 и принимает
(accept + `SEND`/`RECV`) ровно двух пиров подряд на том же канале,
чтобы доказать документированный авто-re-arm (`docs/UNETRTL.md`,
"Passive open (LISTEN)"), затем вызывает `UNLISTEN`. Тестовый клиент
(`unettest_listen_client.py`) закрывает соединение сам сразу после
чтения ответа, поэтому re-arm обычно срабатывает через собственный
`NERR_CLOSED` внутри `RECV` (drain-вызов видит FIN пира), а не через
явный `CLOSE` со стороны `UNETTEST` -- оба пути документированы как
эквивалентные.

Терминал 1 (после того как `UNETTEST` напечатает `listening; connect a
peer now`):

```sh
python3 tools/dev/unettest_listen_client.py --host 192.168.7.2 --port 9000
```

В DSS: `UNETTEST -l 9000 192.168.7.1`.

**Ожидаемо:** после `listening; connect a peer now` запустить терминал 1
-- ожидать `waiting for peer #1`, `peer accepted`, `request sent`,
затем (клиент читает ответ и сам закрывается) `peer closed after
reading reply (re-armed)`. Запустить терминал 1 **второй раз** (`re-arm`
проверяется именно повторным подключением на тот же порт) -- ожидать
`waiting for peer #2`, снова `peer accepted`/`request sent`/`peer
closed after reading reply (re-armed)`, затем `unlisten done`. Если
второе подключение не
проходит -- это находка про сам re-arm; зафиксировать отдельно.
(Harness уже проверяет арминг/таймауты/UNLISTEN этого режима; настоящий
входящий accept возможен только здесь.)

## Сценарий E: non-blocking SEND (`-a`, ASYNCSEND)

`UNETTEST -a` делает `SETOPT SENDSLICE`, затем `CONNECT HOST:PORT`,
затем `SEND` ~1200 байт против пира, который намеренно не читает сокет
(закрывая TCP receive window), чтобы поймать хотя бы один `NERR_AGAIN`.

**Сначала выключить авто-тюнинг приёмного буфера TCP**, иначе сценарий
физически не может отработать: macOS переписывает `SO_RCVBUF` на
принятом сокете, окно получается в несколько килобайт, все 1200 байт
влезают за один раз и `SEND` приостанавливаться не обязан.

Терминал 1:

```sh
sudo sysctl -w net.inet.tcp.doautorcvbuf=0
python3 tools/dev/unettest_asyncsend_stall.py --bind 192.168.7.1 --port 8080
sudo sysctl -w net.inet.tcp.doautorcvbuf=1   # вернуть после теста
```

В DSS: `UNETTEST -a 192.168.7.1 8080`.

**Первым делом смотреть на строку `accepted socket rcvbuf=`** в выводе
скрипта. Если там не запрошенные 700, а несколько тысяч -- авто-тюнинг
всё ещё включён, скрипт напечатает `WARNING`, и результат прогона
ничего не значит независимо от того, что показал DSS.

**Ожидаемо:** терминал 1 покажет `CONN from 192.168.7.2:...`, паузу
`--stall` секунд, затем `drained N bytes total` (N должно быть 1200).
В DSS -- одну или несколько строк `SEND suspended (NERR_AGAIN),
confirmed so far: <n>`, затем `request sent` и `resumes needed: <k>`
(k >= 1 подтверждает, что `NERR_AGAIN`/resume реально отработали, а не
молча проскочили; старый smoke-тест покрывает k=0; новый режим -r в harness
проверяет также задержанный ACK и реальные возобновления).

Если `resumes needed: 0` при выключенном авто-тюнинге -- подбирать
параметры в узком коридоре, а не наугад:

- `--rcvbuf` должен быть **больше** `TCP_MSS` (536), иначе ни один
  сегмент не влезает, DLL не отправляет вообще ничего и в терминале 1
  видно `drained 0 bytes`. Значения по умолчанию (700) достаточно;
  уменьшать его -- ровно неверное направление.
- `--stall` должен быть заметно **меньше** бюджета повторов DLL,
  `ASYNC_MAX_AGAIN * ASYNC_SLICE_MS` = 20 * 150 мс = 3000 мс. При
  `--stall 3` они совпадают, и прогон превращается в гонку: DLL
  исчерпывает бюджет и `SEND` падает вместо возобновления.

## F. Полный ответ, начавшийся во время SEND (0.3.1)

На хосте: `python3 tools/dev/unettest_response_server.py --port 8080`.
На DSS после NETCFG/IFUP:

```
UNETTEST -r 0 192.168.7.1 8080
UNETTEST -r 25 192.168.7.1 8080
```

Указать реальный адрес хоста в сети стенда. Ожидается:

```
[R1] first8=485454502F312E31
[R2] length=8233 crc32=62763860
resumes needed: N
RESULT OK
```

Проверяются все байты HTTP-заголовка и тела 8192 байта, LOST и EOF.
Сервер отвечает сразу после полного PROPFIND. Обычный сокет не гарантирует
совмещение ACK с данными и конкретную сегментацию; `N=0` допустимо здесь.
Host-стенд дополнительно проверяет ненулевые возобновления, ACK отдельно и
с payload, FIN отдельно и с payload, сегменты 536/1460, маленькие буферы,
полную очередь, второй канал, перекрытия и ошибки ACK.

Сохранить вывод обоих запусков, хеш DLL/образа и tcpdump с sequence/ACK/window.
Затем повторить SNC с исходным WebDAV-сервером и сохранить аналогичную трассу.
До этих прогонов host-результат не считается приёмкой в MAME/на железе.

## G. Пропускная способность receive-window (0.3.2--0.3.7)

На доступной MAME стороне pcap-сети запустить сервер с тем же размером файла,
на котором до исправления наблюдалось около 54 KB/s:

```
python3 -u tools/dev/dlspeed_server.py --bind 192.168.7.1 --port 18081 --count 4194304
```

На DSS после `NETCFG`/`IFUP`:

```
DLSPEED http://192.168.7.1:18081/test.bin
```

Подставить реальный адрес peer-а из топологии pcap. Ожидаются точные 4194304
байта, `Integrity: OK`, `RESULT OK` и скорость не ниже прежних примерно
54 KB/s. Параллельно сохранить pcap с TCP port 18081. DLSPEED передаёт
буфер 2144 байта; вместе с pending-очередью 536 байт это открывает максимальное
окно 2680 байт. В SYN от UNETRTL 0.3.7 должен быть receive MSS 536: буфер
принимает ровно четыре сегмента, а pending-очередь -- пятый. MSS 1460 из 0.3.6
оставлен только прямым клиентам, поскольку на синхронном DLL RECV он дал
stop/start-регрессию. Исходящий SEND также режется по 536 байт. Для SNC с буфером
2048 байт сегмент, пересекающий границу caller-buffer, должен сохранить
помещающийся хвост в durable pending; следующий RECV должен добавить его к
новым данным, а не потерять. ACK не должен
продвигать receive sequence за данные, ещё не записанные в caller-buffer или
durable pending. Сохранить вывод DLSPEED, вывод сервера, pcap, SHA-256 DLL и
образа; без этого ручного прогона host-suite подтверждает регрессию, но не
MAME/pcap throughput.

## H. FIN пира во время SEND (0.3.8)

Воспроизводит багрепорт со стороны SNC/WebDAV: сервер отвечает и
закрывает соединение, не дочитав тело `PUT`. До 0.3.8 `SEND` отдавал
`nerr=05 tcp=00` (общая ошибка отправки вообще без TCP-причины); теперь
это `NERR_CLOSED` с отдельной причиной `F_CLOSED`.

Обычный сокет-сервер такую ситуацию не создаёт: ядро подтверждает всё
принятое, и к моменту ответа исходящий кусок уже подтверждён -- `SEND`
просто завершается успехом. Поэтому, как и в сценарии E, нужно
**сначала выключить авто-тюнинг приёмного буфера**:

Терминал 1:

```sh
sudo sysctl -w net.inet.tcp.doautorcvbuf=0
python3 tools/dev/unettest_fin_during_send.py --bind 192.168.7.1 --port 8080
sudo sysctl -w net.inet.tcp.doautorcvbuf=1   # вернуть после теста
```

Терминал 2 (по желанию, но именно он доказывает вторую половину
исправления -- что ответ принят и подтверждён, а не выброшен):

```sh
sudo tcpdump -i feth0 -n -e -vv 'tcp port 8080'
```

В DSS: `UNETTEST -a 192.168.7.1 8080`.

**Сначала читать лог скрипта.** Строка `accepted socket rcvbuf=` должна
показывать запрошенные 700, а `N bytes queued unread at FIN time` -- от
одного сегмента до значения меньше 1200. Если скрипт напечатал
`WARNING`, прогон ничего не значит, каким бы ни был вывод DSS.

**Ожидаемо в DSS:**

```text
Send failed.
lasterr: RTL hw=1/#0300 st=SEND nerr=07 tcp=08 res=00 tx=04/02/01/22
```

Ключевое -- пара `nerr=07 tcp=08` (`NERR_CLOSED` / `F_CLOSED`). Старая
0.3.7 на том же стенде даёт `nerr=05 tcp=00`, это и есть регрессионный
признак. Перед этим допустимы строки `SEND suspended (NERR_AGAIN)` и
ненулевой счётчик подтверждённых байт.

В tcpdump должен быть виден кумулятивный ACK Sprinter-а, покрывающий и
байты ответа, и FIN: полезная нагрузка сохраняется в pending-очередь ДО
продвижения receive sequence, поэтому подтверждение ответа означает, что
он доступен последующим `RECV`. Обратное (ответ подтверждён, но
выброшен) -- как раз то, что делал бы старый путь `F_RST`.

Строку `lasterr:` теперь можно снимать не сразу: с 0.3.8 она
замораживается в момент отказа, и успешный промежуточный вызов
(например попытка дочитать ответ) её не затирает. До 0.3.8 такой вызов
превращал `st=SEND nerr=07` в собственный `st=RECV nerr=00`.

`UNETTEST` сам после неудачного `SEND` очередь не дочитывает (у него нет
такого режима), поэтому прикладную половину -- что ответ действительно
читается вызовами `RECV` после `NERR_CLOSED` -- закрывает либо host-suite
(`tools/test-exe-dll.js`, три вектора: ответ+FIN одним сегментом, двумя
сегментами, и многосегментный SEND с побайтовой проверкой провода), либо
повторный прогон SNC с исходным WebDAV-сервером: в его логе должна
появиться строка `* HTTP NNN` вместо потери статуса.

Сохранить: вывод DSS, полный лог скрипта, pcap, SHA-256 `UNETRTL.DLL` и
`distr/sprinter-rtl8019a.img`.

## 0.4.2: окно передачи и окончательная ошибка SEND

RTL учитывает окно пира и повторяет только неподтверждённый хвост. `DE`
всегда равен подтверждённому префиксу исходного вызова (0..IX), в том числе
после нескольких `NERR_AGAIN`. Возобновлять вызов нужно с прежними каналом,
указателем и длиной. Пустой допустимый ACK больше не вызывает ответный ACK.

При нулевом окне идут однобайтовые пробы: примерно через 1, 2, затем каждые
4 секунды. Ответы живого пира сохраняют соединение; четыре последовательные
безответные пробы завершают SEND ошибкой. При `SENDSLICE=0` живой пир может
удерживать блокирующий вызов неограниченно долго; внутренние интервалы
ограничены, отмена через `CANCELKEYS` сохраняется. Ненулевой SENDSLICE
расходуется и на обработку ACK, без запуска нового кванта на каждый пакет.
Интервалы пока считаются итерациями; переход на системные таймеры отложен.

После окончательного тайм-аута, ошибки NIC или отмены SEND канал занят до
CLOSE/NETDONE. Повторный SEND возвращает `NERR_CLOSED`, `DE=0`, ничего не
передавая. RECV сначала выдаёт сохранённые данные, затем `NERR_CLOSED`;
STATUS снимает признак соединения. CLOSE посылает RST и освобождает канал
или возвращает его в LISTEN. FIN/RST пира обрабатываются отдельно.

Host-тесты настоящей DLL покрывают WIN1/WIN2, окно 163 при SEND 244,
частичный ACK с нулевым окном, паузы 6/15/30 секунд, потерянное открытие
окна, исчезновение пира, старые ACK и переполнение sequence numbers.
Приёмка MAME: Battleship n3, те же паузы, ровно 48800 байт, SHA-256
`acc7ecb1abac0482...`, штатное закрытие, без полноразмерных повторов в
нулевое окно и ACK-шторма. Краткие отчёты сохраняются в `docs/evidence/`,
сырые результаты -- локально в `build/evidence/`.

Повторяемая сборка: sjasmplus 1.22.0, sprinter-mkdll/libman 1.3,
`make test-host package image`. Дата L1-заголовка зафиксирована в build.sh:
2026-10-20. Повторный `make build` должен сохранить SHA-256 UNETRTL.DLL.


## 0.4.3: FIN, отмена SEND и UDP

Продолжение SEND после `NERR_AGAIN` проверяется до признака FIN пира.
При обычном полузакрытии оставшиеся сегменты и новые SEND разрешены,
`DE` сохраняет подтверждённый префикс; STATUS сохраняет `UNET_ST_CONN`
до дочитывания очереди через RECV. Окончательная ошибка SEND по-прежнему
снимает этот флаг и запрещает новые передачи до CLOSE/NETDONE.

CLOSE на канале приостановленного SEND теперь отменяет его, посылает RST
и освобождает канал либо перевооружает LISTEN. Возобновлять отменённый
вызов нельзя. CLOSE другого канала возвращает `NERR_BUSY`; NETDONE
отменяет SEND и закрывает оба канала. Это позволяет ограничить ожидание
живого пира с нулевым окном временем, выбранным потребителем.

UDP другого канала в голове кольца вызывает `NERR_AGAIN`, сохраняя TCP.
Нужно прочитать UDP через RECV на его канале и повторить исходный SEND.
TCP ACK/FIN/RST при этом остаются для продолжения SEND. В RTL `NERR_AGAIN`
означает также исчерпание кванта на обработку ACK/обновлений окна, а не
только тишину. Комментарии замороженного зеркала `unet.inc` сохраняют
исходную формулировку ESP; уточнения RTL находятся здесь и в UNETRTL.md.
Другие бэкенды в этом изменении не менялись.

CLOSE ждёт ACK, покрывающий FIN, или RST. Непокрывающий ACK, данные и FIN
пира расходуют остаток общего интервала, не завершают CLOSE успешно и
не начинают интервал заново. Три попытки по 500 итераций сохраняются.
Тесты проверяют старые значения `TCP_LAST_FAIL=0/2`, нулевое окно и эхо
во время закрытия на обеих позициях DLL.

Системные таймеры остаются отдельной задачей. Измерения стенда MAME от
2026-10-20: SENDSLICE=50 давал до 71 мс; интервалы проб с бюджетом 2/4 с
занимали 2.70/5.37 с, то есть примерно 1.35 от номинала. Коэффициент
зависит от CPU, пакетов и прерываний и не является гарантией для железа.


## 0.4.4: регрессии повторной проверки

- Блокирующий SEND (`SENDSLICE=0`) не возвращает `NERR_AGAIN`. Чужая UDP-
  датаграмма в голове NIC отбрасывается, ожидание TCP продолжается, следующий
  RECV её канала получает `UNET_RXF_LOST`. С ненулевым SENDSLICE датаграмма
  сохраняется в NIC: AGAIN позволяет прочитать её и продолжить тот же SEND.
  CLOSE/NETDONE также могут отбросить чужой UDP, отмечая LOST, и продолжают
  прежнюю попытку ожидания ACK FIN вместо немедленного TIMEOUT.
- Каждый повтор DNS заново строится из исходного имени и прежнего XID.
  Тесты теряют одну/две попытки и читают широковещательный ARP между ними;
  запросы коротких и 127-символьных имён должны совпадать побайтно.
- Пустые ACK после принятого FIN больше не возвращают `F_CLOSED` по одному
  только CLOSE_WAIT. Проверяются частичный ACK, окно 163, затем нулевое
  окно с пробами и возобновление хвоста, при SENDSLICE=0/50 и WIN1/WIN2.
  Сам новый FIN по-прежнему сообщает закрытие входящего потока.
- FINI отменяет приостановленный SEND через RST, как CLOSE/NETDONE, даже
  если ещё не передан ни один байт. Три передачи FIN означают два повтора.
- RST пира освобождает очередь и канал либо перевооружает LISTEN одинаково
  в публичном RECV и при обработке чужого канала. Уже скопированные в
  буфер приложения байты возвращаются с CLOSED и верным DE. Новый SEND
  в сброшенный поток запрещён, STATUS не оставляет недоступный RXPEND.
- CLOSE с непрочитанными данными завершает соединение через RST. Данные,
  принятые во время ожидания ACK FIN, также вызывают RST, в том числе когда
  их ACK покрывает FIN: пир узнаёт, что приложение эти байты не прочитало.
- UDP SEND другого канала при приостановленном TCP SEND разрешён. Его RECV
  может ждать весь собственный IY, после чего исходный SEND возобновляется.

Общие номера функций и коды ошибок в замороженном `unet.inc` не менялись.
Комментарии копии UNET509B не описывают политику RTL; специфические правила
RTL приведены здесь и в английском UNETRTL.md. Системные таймеры остаются
отдельной задачей. Коммит и тег в рамках этой работы не создаются.

Причина наблюдавшихся опозданий CBL уточнена мейнтейнером стенда: внутренние
CTC/SIO/PIO и внешний сумматор Sprinter меняют одну IRQ0 в модели MAME.
CLEAR внутреннего устройства может затереть внешний запрос, остающийся
высоким. Это наблюдается с обеими картами и не требует правок IRQ в DLL.
Проверка на реальном железе по-прежнему необходима.

## 0.4.5: FIN вне порядка и защита нового SEND

- После отбрасывания сегмента вне порядка или точного дубликата сбрасывается
  FIN перед общим возвратом TCP.RECV. RCV_NXT не меняется, повторный ACK
  указывает на дыру; SEND продолжает ждать свой ACK. Повтор уже принятого
  FIN в CLOSE_WAIT также не завершает новую передачу.
- Принятый FIN с ACK, не покрывающим текущий SEND, по-прежнему возвращает
  `NERR_CLOSED` и подтверждённый префикс в DE. Теперь это терминальная ошибка
  передачи: новый SEND возвращает CLOSED/DE=0 без записи других байтов по
  занятым sequence numbers. Ответ доступен через RECV, STATUS снимает CONN,
  CLOSE/NETDONE освобождает канал через RST. FIN с покрывающим ACK сохраняет
  прежнее полузакрытое поведение и разрешает дальнейший SEND.
- Добавлены 12 host-регрессий в WIN1/WIN2: FIN впереди RCV_NXT после уже
  сохранённого префикса, FIN впереди и повторный FIN во время SEND с
  SENDSLICE=0/50, новый SEND после принятого непокрывающего FIN. Все 12
  воспроизводят ошибки на DLL 0.4.4 с SHA-256 `5da40142...`.
- Во время приостановленного SEND TCP RECV обоих каналов читает только
  очередь в памяти, LISTEN не продвигает accept. UDP RECV другого канала
  читает только доступную голову кольца: TCP ACK в голове оставляет UDP
  за ним до возобновления SEND (пустой результат с XCHAN).
- После RST пира канал освобождён или перевооружён, поэтому новый SEND
  получает `NERR_STATE`. Устаревшие комментарии capabilities в `unet.inc`
  остаются в неизменённом зеркале: фактический GETCAPS равен `0x023F`.
- Сдвиг кода выявил зависимость CH_STATE_ADDR_A от младшего байта адреса:
  второй элемент CH_STATE мог перейти через границу 256 байт. Теперь helper
  увеличивает полный HL. Обычные host smoke-тесты выявили порчу кода при
  промежуточной сборке; она не считается принятым результатом.

Целевые FIN-сценарии проверяются host harness с реальными EXE/DLL, а обычный
стенд Battleship проверяет сохранение поведения TCP в MAME; он не создаёт
потерю данных перед FIN или повтор FIN во время SEND.

## 0.4.6: подсказки RXPEND/XCHAN после ошибки SEND

Пустой оборванный канал больше не ставит RXPEND и не вызывает XCHAN у
другого канала. PEND_HAS_A учитывает очередь и обычный отложенный EOF
(CH_CLOSED=1), но не терминальную ошибку SEND (CH_CLOSED=2). Частичное
чтение ответа сохраняет подсказки, полное вычерпывание снимает их. Обычный
FIN по-прежнему требует RECV, который сообщает EOF и освобождает канал.

После окончательного NERR_SEND/HW/CANCEL либо CLOSED из-за непокрывающего
FIN в SEND приложение обязано вызвать CLOSE либо NETDONE, даже если уже
вычерпало ответ через RECV. RST пира по-прежнему освобождает канал или
перевооружает LISTEN сразу и не оставляет оборванный слот.
Пустой RECV сообщает CLOSED/DE=0, но не освобождает такой канал и не
перевооружает LISTEN. Новый SEND остаётся запрещён до явного закрытия;
поздний покрывающий ACK не отменяет терминальную ошибку.
STATUS пустого оборванного, но ещё не закрытого исходящего TCP-канала равен
0, как у свободного слота. CONNECT и LISTEN возвращают NERR_STATE до CLOSE;
одного STATUS недостаточно, чтобы считать такой слот доступным повторно.

Регрессии: оба канала, WIN1/WIN2, тайм-аут или непокрывающий FIN, пустая
очередь и частично/полностью прочитанный ответ. Проверяются STATUS,
повторный RECV другого TCP/UDP-канала, запрет новой передачи и освобождение
через CLOSE. Контрольные случаи обычного FIN проверяют сохранение отложенного
EOF и прежнего освобождения после RECV.

Адресные helpers PEND_LEN/OFF_ADDR_A, CLOSED_ADDR_A и LOST_ADDR_A теперь
увеличивают полный HL, поэтому переход младшего байта через FF безопасен.
Удалена недостижимая повторная проверка ACK_WAIT_ACTIVE в DLL-ветке
TCP.RECV.NORMAL_RETURN. Логика SEND, persist, таймеры и общий ABI не менялись.
После пятой проверки добавлены ASSERT на шаги PEND_CLEAR_A:
CH_PEND_OFF = CH_PEND_LEN + 4 и CH_LOST = CH_CLOSED + 2. Они проверяют
константные BSS-смещения и не добавляют байтов или релокаций в DLL.

## Кандидат 0.4.7: независимый квант SEND

При SENDSLICE != 0 отправка уступает управление между отдельными шагами
передачи и приёма. AGAIN с DE=0 допустим даже при немедленном ACK.
Продолжения обязаны сохранять канал, указатель, длину и байты; между ними
проверяются RECV/STATUS. Блокирующий режим сохраняется.

Приёмка: новые frozen inputs с хешем кандидата, DIRECT/MQTT perf, faults,
exit и десятиминутный load с audio Off и native speed. Исходные frozen
inputs не изменять. Записать каждый максимум dispatcher + DLL, физический
input-to-PRESENT и pcap drops; проверить игру/rematch/chat и выход DSS.
Цель <=10 мс относится к исправной NIC; ожидания аппаратных ошибок и
восстановления кольца измеряются отдельно. До этих замеров кандидат
не считается прошедшим MAME или аппаратную приёмку.
